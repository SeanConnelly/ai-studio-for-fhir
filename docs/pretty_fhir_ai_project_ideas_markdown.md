# AI + FHIR Application Specification

This document defines twelve AI + FHIR healthcare application scenarios as product specifications suitable for handoff to a code agent. It separates **common UI components** from scenario-specific views so that repeated patterns such as the patient banner, evidence panel, timeline, action bar, and AI-generated text blocks can be implemented once and reused across scenarios.

Each scenario must make the AI-generated content explicit. Any text generated by AI should be clearly labelled in the UI, reviewable by the user, grounded in source data, and editable before it is saved, sent, or used for clinical action.

---

# 1. Product Principles

## 1.1 Core goals

The applications should help users:

- Understand the patient or cohort context quickly.
- See relevant FHIR-derived evidence without navigating multiple systems.
- Receive AI-generated summaries, explanations, drafts, or recommendations.
- Review the evidence behind AI outputs.
- Take an action directly from the screen.
- Preserve a clear audit trail of user decisions and generated content.

## 1.2 AI content rules

All AI-generated content must be visually distinct from source data.

AI-generated content must:

- Be labelled with a heading such as **AI-generated summary**, **AI-generated draft**, or **AI-generated recommendation**.
- Include a short explanation of what source data was used.
- Be editable before saving or sending.
- Avoid pretending to be a clinician decision.
- Include a user review state: `Draft`, `Reviewed`, `Edited`, `Approved`, `Rejected`.
- Retain source references where available.
- Never overwrite FHIR source data.

Recommended UI label:

```text
AI-generated draft — requires clinician review before use
```

## 1.3 Common workflow pattern

Most scenarios follow this flow:

1. Select patient, cohort, result, request, or question.
2. Pull relevant FHIR resources.
3. Show structured source evidence.
4. Generate scenario-specific AI text.
5. Let the user review and edit the AI output.
6. Let the user create a task, note, message, referral, order, report, or dashboard item.
7. Save audit metadata.

# 2. Common UI Components

These components should be reusable across the application scenarios. Scenario sections reference these components by ID.

---

## CC-01 Patient Banner

Used when a scenario is patient-specific.

### Purpose

Provides immediate patient identity, safety, and context information.

### Fields

| Field | Description |
|---|---|
| Patient name | Full name from `Patient.name` |
| Age / DOB | Calculated age and date of birth |
| Sex / gender | From `Patient.gender`, with local display rules |
| Patient identifier | NHS number, MRN, or local patient ID |
| Current setting | Inpatient, ED, outpatient, discharged, community |
| Responsible team | Current care team, GP, consultant, or service |
| Alerts | Allergies, infection risk, safeguarding, language needs |
| Contact preference | Phone, portal, letter, carer contact where available |

### Behaviour

- Remains visible at the top of patient-level screens.
- Provides quick links to demographics, encounters, allergies, medications, and care team.
- Displays a warning if patient identity is incomplete or ambiguous.

---

## CC-02 Context Summary Card

### Purpose

Shows the clinical or operational context for the current workflow.

### Fields

| Field | Description |
|---|---|
| Current problem / reason | Why this screen is being shown |
| Linked encounter | Encounter associated with the workflow |
| Relevant conditions | Short list of relevant active or historical conditions |
| Relevant medications | Active medications relevant to the scenario |
| Relevant observations | Recent labs, vitals, scores, or measurements |
| Current status | Open, pending, completed, overdue, escalated |

---

## CC-03 Evidence Panel

### Purpose

Shows the source data used by the application and by the AI output.

### Fields

| Field | Description |
|---|---|
| Source resource | FHIR resource type and display name |
| Date / time | When the source data was authored, observed, or updated |
| Author / performer | Clinician, organization, lab, device, or system |
| Key value | Result, diagnosis, note excerpt, medication, procedure, etc. |
| Confidence / match reason | Why this source was selected |
| Link to source | Opens raw source detail or document |

### Behaviour

- Evidence items should be expandable.
- AI-generated outputs should reference the evidence items used.
- If evidence is missing, stale, conflicting, or incomplete, show a warning.

---

## CC-04 Timeline

### Purpose

Shows clinically relevant events in chronological order.

### Typical events

- Encounter started / ended
- Test ordered
- Test resulted
- Medication started / stopped
- Diagnosis recorded
- Appointment booked / missed
- Task created / completed
- Message sent
- Referral made
- Care plan updated

### Behaviour

- Supports filtering by event type.
- Highlights overdue or unresolved events.
- Allows drill-down into the source FHIR resource.

---

## CC-05 Status and Risk Badge Bar

### Purpose

Provides immediate prioritisation.

### Example badges

| Badge | Meaning |
|---|---|
| Critical | Immediate action required |
| Urgent | Action required soon |
| Overdue | Expected follow-up date has passed |
| Incomplete evidence | Required data is missing |
| Patient not informed | No communication evidence found |
| Draft AI output | Generated text requires review |
| Closed loop | Follow-up is complete |

---

## CC-06 Action Bar

### Purpose

Allows the user to act from the current workflow.

### Common actions

- Assign owner
- Create task
- Create note
- Create referral
- Create order
- Notify patient
- Notify GP / care team
- Schedule appointment
- Mark reviewed
- Mark no action required
- Escalate
- Close loop
- Export / copy summary

### Behaviour

- Actions should be permission-aware.
- Potentially irreversible actions require confirmation.
- AI-generated content must be reviewed before it can be saved, sent, or attached.

## CC-07 AI Generated Text Panel

### Purpose

Standard component for all AI-generated text.

### Required structure

```text
[AI-generated <content type>]
Status: Draft / Reviewed / Edited / Approved / Rejected
Generated from: <short list of source data categories>
Intended audience: <clinician / patient / admin / care manager / family caregiver>
Review requirement: <who must review before use>

<generated text body>

Actions:
[Regenerate] [Edit] [Approve] [Copy] [Save as note] [Send] [Reject]
```

### Required metadata

| Field | Description |
|---|---|
| Prompt type | Summary, explanation, justification, outreach message, triage note, etc. |
| Audience | Clinician, patient, care manager, admin, researcher, family caregiver |
| Source resources | FHIR resources used |
| Generated timestamp | When text was generated |
| Model identifier | AI model or service used, if available |
| Reviewer | User who approved or edited the output |
| Final disposition | Saved, sent, rejected, copied, attached, ignored |

---

## CC-08 AI Safety and Quality Checklist

### Purpose

Ensures generated text is safe enough for review and use.

### Checklist items

| Check | Description |
|---|---|
| Grounded in visible evidence | User can see the source data behind the text |
| No unsupported diagnosis | AI does not invent diagnoses not present in source data |
| No hidden action | AI does not perform external actions without user approval |
| Appropriate audience | Patient-facing text is plain language; clinician-facing text is concise and technical |
| Uncertainty shown | Missing or conflicting evidence is explicitly stated |
| Editable | User can modify before saving or sending |

---

## CC-09 Source Data Completeness Panel

### Purpose

Shows whether enough data exists to support the workflow.

### Fields

| Field | Description |
|---|---|
| Required data | Data needed for the scenario |
| Found data | Data available in FHIR resources |
| Missing data | Data not found |
| Staleness | Whether data is recent enough |
| Impact | How missing data affects the output |

### Example

```text
Missing evidence:
- No recent eGFR found in the last 90 days.
- No documented patient communication found after the abnormal result.
- No current medication statement found, only medication requests.
```

# Scenario 1: Smart Patient Summary Generator

## Purpose

Creates a concise, clinician-friendly or role-specific summary of a patient from FHIR data.

## Primary users

- ED doctor
- Ward clinician
- Care manager
- Patient
- Family caregiver

## Common components used

- CC-01 Patient Banner
- CC-02 Context Summary Card
- CC-03 Evidence Panel
- CC-04 Timeline
- CC-07 AI Generated Text Panel
- CC-08 AI Safety and Quality Checklist
- CC-09 Source Data Completeness Panel
- CC-10 Review and Audit Panel

## FHIR resources

`Patient`, `Condition`, `MedicationRequest`, `AllergyIntolerance`, `Observation`, `Encounter`, `CarePlan`, `DocumentReference`

## Unique views

### 1. Summary Audience Selector

Allows the user to select the intended audience before generation.

Options:

- ED doctor
- Inpatient clinician
- Care manager
- Patient
- Family caregiver

The selected audience changes tone, detail level, and output structure.

### 2. Current Issues View

Displays active conditions, current medications, allergies, abnormal observations, open care plans, and recent encounters.

### 3. Recent Changes View

Highlights changes since a configurable date, such as:

- New diagnoses
- Medication starts or stops
- New abnormal results
- Recent admissions or ED visits
- New care plan goals

## AI-generated text requirements

### AI-GEN-01: Clinician Summary

Must be visibly labelled:

```text
AI-generated clinician summary — requires clinical review
```

Required content:

- One-line patient overview
- Current active issues
- Recent clinical changes
- Active medications relevant to current issues
- Allergies and safety alerts
- Abnormal or pending results
- Risks and follow-up items
- Gaps or missing evidence

Example output:

```text
AI-generated clinician summary — requires clinical review

Sarah Ahmed is a 67-year-old woman with COPD, hypertension, and recent ED
attendance for cough and breathlessness. Key current issues are persistent
respiratory symptoms, documented weight loss, and a final chest X-ray report
showing a right upper zone opacity requiring CT follow-up.

Recent changes:
- ED attendance on 21 May 2026 for cough and breathlessness.
- Doxycycline prescribed on discharge.
- Final radiology report issued after discharge with recommended CT chest.

Risks / follow-up:
- No CT order or respiratory referral found.
- No documented patient communication found after the final report.
- Consider urgent follow-up owner assignment and patient contact.

Missing evidence:
- No prior chest imaging found in the last 12 months.
```

### AI-GEN-02: Patient-Friendly Summary

Must translate clinical information into plain language.

Required content:

- What is currently happening
- What has changed recently
- What the patient may need to do next
- Questions to ask the care team
- Safety-net language

## User actions

- Generate role-specific summary
- Edit summary
- Save as clinical note
- Copy to handover
- Send patient-friendly version through communication workflow
- Create follow-up task from summary item

## Acceptance criteria

- User can generate at least two role-specific summaries for the same patient.
- AI output clearly changes tone and structure by audience.
- All generated summaries list the source data categories used.
- User can edit and approve before saving.
- Missing evidence is explicitly shown.

# Scenario 2: FHIR Prior Authorization Copilot

## Purpose

Helps staff prepare prior authorization requests by pulling diagnosis, medication history, procedures, observations, and supporting evidence from FHIR data.

## Primary users

- Prior authorization staff
- Clinicians
- Pharmacy team
- Revenue cycle team

## Common components used

- CC-01 Patient Banner
- CC-02 Context Summary Card
- CC-03 Evidence Panel
- CC-05 Status and Risk Badge Bar
- CC-06 Action Bar
- CC-07 AI Generated Text Panel
- CC-08 AI Safety and Quality Checklist
- CC-09 Source Data Completeness Panel
- CC-10 Review and Audit Panel

## FHIR resources

`Patient`, `Coverage`, `Condition`, `MedicationRequest`, `Procedure`, `Observation`, `DocumentReference`, `Encounter`

## Unique views

### 1. Requested Service / Medication Panel

Captures the prior authorization target.

Fields:

- Medication, procedure, imaging, or service requested
- Requested date
- Requesting clinician
- Payer / coverage
- Indication entered by user
- Required documentation checklist

### 2. Supporting Evidence Finder

Shows candidate evidence grouped by type:

- Diagnoses supporting medical necessity
- Medication history and failed therapies
- Relevant procedures
- Relevant lab results or observations
- Prior notes or documents
- Coverage details

### 3. Missing Evidence Checklist

Highlights what may be needed before submission.

Examples:

- No recent HbA1c found.
- No documented trial of first-line medication found.
- No specialist note found in last 12 months.
- No relevant imaging report attached.

## AI-generated text requirements

### AI-GEN-03: Prior Authorization Justification Draft

Must be visibly labelled:

```text
AI-generated prior authorization justification — requires staff and clinician review
```

Required content:

- Requested medication or procedure
- Patient diagnosis and clinical indication
- Relevant history
- Previous therapies tried
- Objective evidence
- Why the requested item is medically necessary
- Missing evidence or uncertainty

Example output:

```text
AI-generated prior authorization justification — requires staff and clinician review

Request: GLP-1 receptor agonist therapy for type 2 diabetes.

Clinical rationale:
The patient has type 2 diabetes with suboptimal glycaemic control despite
current therapy. Recent observations show HbA1c of 9.4% within the last three
months. Medication history indicates current metformin therapy and prior trial
of sulfonylurea, which was discontinued due to documented hypoglycaemia.

Supporting evidence found:
- Type 2 diabetes diagnosis recorded on the active problem list.
- HbA1c 9.4% on 12 May 2026.
- Current metformin prescription.
- Prior sulfonylurea discontinuation note.

Missing or incomplete evidence:
- No recent weight or BMI found in the last six months.
- No payer-specific step therapy policy found in available documents.
```

### AI-GEN-04: Missing Evidence Explanation

Generates a short explanation of missing documentation and why it matters.

## User actions

- Select requested medication or procedure
- Generate supporting evidence list
- Generate justification draft
- Attach evidence
- Create checklist task
- Export prior authorization packet
- Mark as submitted

## Acceptance criteria

- User can enter a requested item and see relevant diagnoses, observations, medication history, and documents.
- AI-generated justification is separated from source evidence.
- Missing evidence is displayed before export.
- User can edit final justification.

# Scenario 3: Gaps-in-Care Finder for Preventive Screening

## Purpose

Identifies patients who may be overdue for screenings, vaccines, or chronic disease follow-ups.

## Primary users

- Population health team
- GP practice team
- Care coordinators
- Quality improvement staff

## Common components used

- CC-01 Patient Banner for patient detail
- CC-03 Evidence Panel
- CC-05 Status and Risk Badge Bar
- CC-06 Action Bar
- CC-07 AI Generated Text Panel
- CC-09 Source Data Completeness Panel
- CC-11 Worklist View
- CC-12 Patient Communication Composer

## FHIR resources

`Patient`, `Immunization`, `Observation`, `Condition`, `Procedure`, `Encounter`, `Communication`, `Task`

## Unique views

### 1. Population Gaps Worklist

Shows patients with open gaps.

Columns:

- Patient
- Gap type
- Rule triggered
- Last completed date
- Due date
- Risk level
- Outreach status
- Assigned owner
- AI-generated outreach summary

### 2. Rule Detail Panel

Explains why the patient is considered overdue.

Example rules:

- Diabetes with no HbA1c in defined period
- Mammogram overdue based on screening interval
- Flu / COVID vaccination missing
- Blood pressure follow-up overdue

### 3. Outreach Campaign Builder

Lets user select patients and generate patient-specific messages.

## AI-generated text requirements

### AI-GEN-05: Care Gap Explanation

Must be visibly labelled:

```text
AI-generated care gap explanation — requires review before outreach
```

Required content:

- Identified care gap
- Why the patient appears due or overdue
- Last relevant evidence found
- Recommended next action
- Missing evidence that may change the conclusion

Example output:

```text
AI-generated care gap explanation — requires review before outreach

This patient appears overdue for HbA1c monitoring. They have an active diagnosis
of type 2 diabetes, and the most recent HbA1c found was 9.1% on 14 November 2025.
No HbA1c result was found in the last six months.

Recommended action:
Invite the patient for repeat HbA1c testing and diabetes review.

Potential uncertainty:
Results from external laboratories may not be available in this record.
```

### AI-GEN-06: Patient Outreach Message

Must be patient-friendly.

Required content:

- Why the patient is being contacted
- What they need to book or complete
- How to get help
- Safety-net note if appropriate

Example output:

```text
AI-generated patient message — requires staff review before sending

Hello Sarah, our records show that you may be due for a diabetes blood test
called HbA1c. This test helps your care team understand how your blood sugar has
been over the last few months. Please contact the practice to book a blood test
or use the booking link if available.
```

## User actions

- Filter gaps by rule, risk, owner, location, or due date
- Assign outreach tasks
- Generate patient messages
- Mark gap as resolved
- Exclude patient with reason
- Create dashboard export

## Acceptance criteria

- Worklist shows at least 2–3 implemented care gap rules.
- Each gap has a rule explanation and evidence trail.
- Outreach messages are generated but not sent without review.
- Users can mark gaps resolved or excluded with reason.

# Scenario 4: Medication Safety and Interaction Assistant

## Purpose

Builds a medication review app that flags possible duplication, interactions, allergy conflicts, or adherence issues using FHIR medication and allergy data.

## Primary users

- Pharmacists
- Clinicians
- Medication review teams
- Patients, for patient-facing counselling output

## Common components used

- CC-01 Patient Banner
- CC-02 Context Summary Card
- CC-03 Evidence Panel
- CC-05 Status and Risk Badge Bar
- CC-06 Action Bar
- CC-07 AI Generated Text Panel
- CC-08 AI Safety and Quality Checklist
- CC-09 Source Data Completeness Panel
- CC-10 Review and Audit Panel
- CC-12 Patient Communication Composer

## FHIR resources

`MedicationRequest`, `MedicationStatement`, `AllergyIntolerance`, `Condition`, `Observation`, `Patient`, `Encounter`, `DocumentReference`

## Unique views

### 1. Active Medication List

Shows current medication requests and statements.

Fields:

- Drug name
- Dose
- Route
- Frequency
- Start date
- Prescriber
- Indication where known
- Status
- Last issued / last confirmed date

### 2. Medication Risk Panel

Groups risks by category.

Risk categories:

- Duplicate therapy
- Allergy conflict
- Drug-condition concern
- Drug-lab concern
- Possible interaction
- High-risk medication
- Adherence concern

### 3. Counselling Summary View

Creates patient-friendly medication guidance.

## AI-generated text requirements

### AI-GEN-07: Medication Review Summary

Must be visibly labelled:

```text
AI-generated medication safety summary — requires pharmacist or clinician review
```

Required content:

- Current active medications
- Key safety concerns
- Evidence for each concern
- Recommended review questions
- Suggested follow-up actions
- Missing medication history or uncertainty

Example output:

```text
AI-generated medication safety summary — requires pharmacist or clinician review

Medication review identified three items for review:

1. Possible duplicate therapy:
Two active NSAID prescriptions were found: ibuprofen and naproxen. Confirm
whether both are intended to be active.

2. Allergy conflict:
The patient has a documented penicillin allergy. No active penicillin-class
medication was found.

3. Monitoring consideration:
The patient is taking an ACE inhibitor and has not had a recent renal function
or potassium result in the last six months.

Suggested follow-up:
Confirm actual medication use with the patient and consider renal function and
potassium monitoring if clinically appropriate.
```

### AI-GEN-08: Patient Medication Counselling Text

Required content:

- Plain-language explanation
- What to take and when
- What to watch for
- What to ask the pharmacist or clinician
- Clear warning not to stop medicines without clinical advice

## User actions

- Reconcile medication list
- Mark medication as current / not current
- Create pharmacist review task
- Generate clinician note
- Generate patient counselling summary
- Escalate high-risk medication issue

## Acceptance criteria

- Active medication list distinguishes requests from patient-reported statements.
- AI summary identifies concerns with evidence.
- Patient counselling text is plain-language and reviewable.
- No medication change is made automatically.

## Purpose

Matches patients to trial eligibility criteria using coded clinical data and relevant unstructured documents.

# 8. Final Product Framing

This product suite should be framed as:

> A reusable AI + FHIR application framework that combines structured clinical data, source evidence, AI-generated text, and reviewable user actions across multiple healthcare workflows.

The most important implementation principle is that every scenario should clearly separate:

1. **Source data** from FHIR or documents.
2. **AI-generated interpretation or draft text**.
3. **Human-reviewed actions** taken by the user.
4. **Audit evidence** showing what was generated, reviewed, changed, saved, sent, or closed.

That separation is what makes the applications reusable, clinically safer, and easier for a code agent to implement consistently.
